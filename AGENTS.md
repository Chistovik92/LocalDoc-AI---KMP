# Системные инструкции для AI-агента (LocalDoc AI — KMP)

## Архитектурные правила

1. **Строгая изоляция платформенного кода.** В `commonMain` пишется только чистый Kotlin,
   бизнес-логика (`SmartPipeline`) и UI (`Compose Multiplatform`). Любые системные вызовы
   оформляются через `expect/actual`.
2. **Безопасность памяти в C++ (`cpp_core/`).**
   - Запрещено использовать сырые указатели без проверки на `nullptr`.
   - Вся работа с `llama.cpp` идёт строго через чистый C-интерфейс (`localdoc_c_api.h`),
     чтобы iOS `cinterop` и Android JNI вызывали одни и те же функции без дублирования.
3. **Кроссплатформенный RAG.** Не использовать платформо-специфичные БД (ObjectBox и т.п.)
   в общих модулях. Векторное хранилище — `VectorStore` (JSON + KeyValueStore) с
   L2-нормализацией и косинусным поиском; интерфейс `EmbeddingProvider` совместим
   с будущей ONNX-моделью эмбеддингов.
4. **Синхронизация с llama.h.** Сабмодуль `cpp_core/llama.cpp` пиннут на тег `b10004`.
   Перед изменением сигнатур C-кода сверяться с `cpp_core/llama.cpp/include/llama.h`.

## Стиль кода

- Kotlin: строгая типизация, корутины (`Flow`) для стриминга, никаких блокирующих вызовов
  на главном потоке (`Dispatchers.IO` для файлов, сети и инференса).
- C++: стандарт C++17, аккуратное управление KV-кэшем llama.cpp, обязательное освобождение
  всех ресурсов (`localdoc_free`), атомарные флаги отмены генерации.
- UTF-8: в C-мосте токены отдаются в UI только завершёнными UTF-8 последовательностями
  (критично для кириллицы).
- Коммиты: короткие по смыслу, каждый шаг = один коммит; структуру папок не нарушать.

## Проверка сборки

- Android: `./gradlew :composeApp:assembleDebug` (нужны Android SDK + NDK).
- iOS: `./cpp_core/scripts/build_ios_xcframework.sh` и
  `./gradlew :composeApp:linkDebugFrameworkIosSimulatorArm64` (macOS + Xcode).

## Тестирование на устройстве (adb)

- **Никогда не делать `adb uninstall` без бэкапа данных.** `uninstall` стирает всю внутреннюю
  память приложения (`/data/data/com.localdoc.ai` — книги, настройки, прогресс, автобэкапы)
  безвозвратно. Перед любым `uninstall` снять копию: `scripts/adb-backup.ps1`.
- Debug-APK подписан debug-ключом и не ставится поверх release (`INSTALL_FAILED_UPDATE_INCOMPATIBLE`).
  Ставить поверх release можно только APK, подписанный тем же release-ключом.
- Чтобы не потерять данные при смене ключа подписи: сначала `scripts/adb-backup.ps1`, затем `uninstall`,
  затем `install` — и восстановить данные из бэкапа.

## Документация

- Планы — только в `ROADMAP.md`; история выпущенного — в `CHANGELOG.md`; не дублировать одно и то же в двух местах.
- Появился новый план, баг или пожелание — сразу записать в `ROADMAP.md` под нужной версией.
- Порядок выпуска версии (номера, CHANGELOG, `.github/release-notes.md`, тег, проверка подписи) — в `README.md`, раздел «Выпуск версии».

## Процесс выпуска версии (с 2.4.2)

Каждая версия — **отдельная ветка `release-<версия>`** и проходит полный цикл до релиза; в `main`
правки выпускаемыми версиями напрямую не пишутся. Порядок:

1. От `main` отводится ветка `release-<версия>`.
2. В ней — все фичи/фиксы версии (каждый шаг = один коммит).
3. Бампится версия (`versionCode`/`versionName` в `build.gradle.kts`, `MARKETING_VERSION` в `iosApp/project.yml`),
   пишутся `CHANGELOG.md` и `.github/release-notes.md`, чистится `ROADMAP.md`.
4. Ветка пушится, создаётся PR; **CI на ветке должен быть зелёным** (Android + iOS).
5. PR мержится в `main`, ветка удаляется.
6. На merge-коммит ставится тег `v<версия>` — релизные workflows собирают подписанный APK и iOS-файлы.
7. Проверяются GitHub Release и отпечаток подписи APK.

Никаких прямых коммитов выпускаемых версий в `main`; `main` меняется только merge'ем ветки.

### Переход на следующую версию и чистка веток

Когда все основные ветки текущей версии замержены в `main` и релиз идёт из `main`, при переходе к
следующей версии `X` (из `0.X.0`): правки делаются **прямо в `main`**, а отыгравшие ветки удаляются —
и локально (`git branch -D`), и на GitHub (`git push origin --delete`). Не копить замерженные ветки.
