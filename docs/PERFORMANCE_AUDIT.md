# Аудит производительности и памяти 2.0.0

Измерения сделаны тестами на синтетических больших данных (`PerformanceAuditTest`, общий код, JVM на ноутбуке разработчика).
Это **не** замеры на телефоне: абсолютные числа на слабом устройстве будут в 3–10 раз больше. Поэтому тест ставит
очень щедрые пределы (десятки секунд) и ловит порядок роста, а не скорость. Замеры на реальных слабых телефонах,
холодный старт и профиль памяти (Android Studio Profiler / Instruments) остаются ручной работой — см. «Не проверено».

## Измерения (JVM, один прогон)

| Сценарий | Данные | Время |
| --- | --- | --- |
| Индексация библиотеки для поиска | 1500 книг × 20 блоков | ~0,5 с |
| Повторная синхронизация индекса без изменений | 1500 книг | ~1 мс |
| Поиск по тексту | 1500 книг, запрос из двух слов | ~0,3 с |
| Запись / чтение списка библиотеки (JSON) | 5000 записей | ~60 мс / ~110 мс |
| Разбор TXT | 12 МБ, 60 000 абзацев | ~1,6 с |
| Разбиение на страницы | 60 000 блоков | ~5 мс |
| Поиск глав | 300 000 блоков | ~120 мс |
| Разбиение на страницы | 300 000 блоков | ~80 мс |

Все этапы линейны по размеру данных; предел в тесте — на порядок выше измеренного.

## Найдено и исправлено

**Запись манифеста индекса поиска на каждую книгу (квадратичный рост).** `FullTextIndex.index` после каждой книги
сериализовал и записывал весь манифест (`docId → подпись`). Первая синхронизация библиотеки из N книг делала N записей по
N записей: на 400 книгах — 400 записей манифеста (красный тест), на 5000 — 5000 записей по ~0,5 МБ в `SharedPreferences`.
Теперь `LibrarySearch.sync` выполняется внутри `FullTextIndex.batch`, манифест пишется один раз в конце. Обрыв посреди
синхронизации безопасен: файлы индекса без записи в манифесте просто строятся заново.

## Проверено, замечаний нет

- **В модель, озвучку и перевод уходит страница, а не книга**: `BookPager` режет текст на страницы по ~1500–6000 символов,
  отдаётся текущая и следующая. Сама открытая книга лежит в памяти списком блоков (для 300 000 блоков — десятки мегабайт).
- **Кэши ограничены**: индекс поиска держит 6 шардов (`CACHED_SHARDS`), картинки — дисковый кэш с лимитом и декодирование с
  `inSampleSize` (> 60 Мпикс не декодируются), страницы PDF рендерятся по одной с ограниченным кэшем.
- **Скачивание и разбор**: ответ читается порциями с жёстким пределом, ZIP — по записям с лимитами 64 МБ / 512 МБ.
- **Корутины**: долгие работы идут в `Dispatchers.IO`/`Default`; `appScope` — единственный долгоживущий скоуп приложения,
  `ReadAloudService` отменяет свой скоуп вместе со службой; собственных `GlobalScope` нет.
- **Холодный старт** (по коду): тяжёлые зависимости объявлены `by lazy` (хранилище секретов, cookie, HTTP-клиент, индексы,
  RAG, синхронизация); при запуске выполняются миграции хранилища (идемпотентны, читают только версию схемы, если она
  актуальна) и чтение списка библиотеки.

## Открыто

1. **Поиск читает шард каждой книги с диска.** Запрос обходит все документы индекса; в памяти держатся 6 шардов, поэтому
   на устройстве запрос по тысячам книг упирается в чтение тысяч файлов (на JVM в памяти — 0,3 с на 1500 книг, на флеш-памяти
   телефона ожидается секунды). Варианты: общий словарь «слово → документы» в одном файле и чтение только нужных шардов;
   отложенный поиск с выдачей по мере готовности. Не сделано: нужны замеры на устройстве, чтобы не усложнять без причины.
2. **Список библиотеки хранится одной JSON-строкой в KV** и записывается целиком при каждой смене прогресса
   (`saveProgress`). На 5000 записей ~60 мс на ноутбуке — на слабом телефоне может быть заметно при частых перелистываниях;
   прогресс стоит писать с задержкой (debounce). Не сделано, чтобы не менять порядок сохранения без проверки на устройстве.
3. **Разбор больших файлов целиком в память.** Входной файл читается в `ByteArray` (см. п. 11 в `SECURITY_AUDIT.md`), а
   ZIP-контейнеры копируют запись при чтении: пик памяти ≈ 2–3 размера файла. Для книг до сотен мегабайт приемлемо.
4. **Тяжёлые парсеры (Mobi, DOC, PDF-OCR)** синхронны и выполняются на фоновом диспетчере; прерывание по отмене только
   между этапами.

## Не проверено

- Холодный и тёплый старт, потребление ОЗУ и батареи на реальных устройствах (Android Go / старые iPhone).
- Утечки на длинных сессиях (профилировщик): код просмотрен, динамически не проверялся.
- Скорость эмбеддингов ONNX — отдельная задача потока C («Замеры скорости и памяти на реальных слабых телефонах»).
